Task: Add "Event photos" feature to logger app

Repo: npm workspaces monorepo (shared, server, client) at repo root. Backend: Express 4 + Zod + Drizzle ORM (better-sqlite3). Frontend: React 18 + Vite + TS + Tailwind + React Router v7 + TanStack Query v5. Node 22 required.

Feature: Allow photo attachments on log entries ("logs" = entries about an event/activity tied to an entity, e.g. a movie watched or restaurant visited). Only categories that support "People" tagging should support photos.

LOCKED-IN DECISIONS
- Scope: Only logs whose category has hasPeople: true in CATEGORY_FIELDS (shared/src/categories.ts) -- currently Movie and Eating Out (not TV, Book, Game) -- can have photos. Enforce this server-side, not just hidden in UI.
- Storage: Local disk under the existing Docker persistent volume (docker-compose.yml mounts a logger-data volume at /app/data; DB_PATH=/app/data/logger.db). New photosDir should derive from path.dirname(config.dbPath) + "/photos" -- reuses the same volume, no Dockerfile/compose changes needed.
- Multiplicity: Multiple photos per log (gallery). Limits: max 10 photos/log, max 10MB/file, allowed types jpeg/png/webp/heic -- validated server-side.
- Upload timing: Supported both at log creation (LogAddForm) and afterward (EntityDetail log view). Implementation: two-step flow -- create the log via existing JSON endpoint first, then upload photos via multipart to the returned logId (no combined JSON+multipart endpoint).
- Deletion: Individual photo deletion supported (delete-confirm UI pattern, matching existing inline-confirm patterns used for notes/logs).
- Thumbnails: Server generates a resized thumbnail on upload using sharp (new dependency), in addition to storing the original file.
- Search: Search results do NOT include real photos -- avoid N+1 queries. Only the EntityDetail log list gets real photos.

KEY EXISTING ARCHITECTURE TO REUSE/RESPECT
- server/src/db/schema.ts: logs table has cascade-delete FK pattern (e.g. entityId -> entities.id with onDelete: "cascade"), and a logPeople join table with a getPeopleForLogs-style batch lookup -- mirror this for a new log_photos table (logId FK -> logs.id onDelete: cascade, plus filename, thumbnailFilename, originalName, mimeType, size, createdAt).
- server/src/services/logService.ts: toLogDTO(row, people) is the single real construction point for LogDTO, used by getLogsForEntity/getLogById/createLog/updateLog. This is where real photos must be joined in (add new getPhotosForLogs(db, logIds) helper mirroring the existing getPeopleForLogs).
- server/src/services/searchService.ts: Does NOT call toLogDTO -- it has two separate manual DTO constructions (an inline LogDTO literal for entity-grouped results, and a toLogWithEntity() function for flat/log-grouped results). Add photos: [] to both -- this cleanly satisfies "search doesn't need photos" without extra suppression logic.
- server/src/services/entityDetailService.ts: getEntityWithLogs() calls getLogsForEntity() so it gets real photos "for free" once logService is updated. getPersonProfile()'s appearances are built manually (like search, not via toLogDTO) -- open question: should these show real photos or photos: []? Recommendation: photos: [] (treat as a summary list, not a detail view) unless told otherwise.
- server/src/config.ts: env-var-driven config object (dbPath, port, authEnabled, etc.) -- add photosDir here.
- server/src/app.ts: Express app with router mounts under /api/* (all except /api/auth and health use requireAuth middleware), then static file serving for the built client SPA, then error handler. Add: (a) ensure photosDir exists at startup via fs.mkdirSync(photosDir, { recursive: true }), (b) app.use("/api/photos", requireAuth, express.static(photosDir)) for serving photo files, (c) mount a new photos router.
- server/package.json: currently has no multer/sharp -- need to add multer, @types/multer, sharp.
- client/src/api/client.ts: the shared request() helper always sets Content-Type: application/json -- need a new helper (e.g. postForm()) that omits that header so the browser sets its own multipart boundary for FormData uploads, while keeping credentials: "include".
- client/src/routes/LogAddForm.tsx and client/src/routes/EntityDetail.tsx (specifically its LogRow component) already conditionally render People-tagging fields based on CATEGORY_FIELDS[category].hasPeople -- gate the new photo UI the same way.
